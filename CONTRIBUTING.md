## Project Structure

| Path | Contents |
|------|----------|
| `VERSION` | Current MMIF version string |
| `specifications/` | Source specification documents (templates) |
| `schema/` | JSON Schema files |
| `vocabulary/` | CLAMS vocabulary source files |
| `docs/` | Published versioned output (generated) |
| `build.py` | Build script: renders templates into `docs/VERSION/` |

The files under `specifications/` are source templates. Do not edit `docs/*/` directly; those are generated by `build.py`.

## Contribution Workflow

1. **Create a branch** from `develop`
2. **Edit source files** in `specifications/`, `schema/`, or `vocabulary/`
3. **Run `python build.py`** to generate versioned output and verify rendering
4. **Test samples** — ensure all JSON examples in `specifications/samples/` validate against the schema
5. **Update `CHANGELOG.md`** describing your changes
6. **Open a pull request** targeting `develop`

For a full release checklist, see the [README](README.md#checklist-for-deployment).

## Writing Technical Specifications

This section defines the standards for specification documents in this repository (primarily `specifications/index.md`).

### Guiding Principle

A specification document is a **reference**, not a tutorial. Readers consult it to answer a precise question; they do not read it linearly. Optimize for scanability and precision over narrative flow.

### Language and Tone

- Use **RFC 2119** keywords to express requirements. Import them by declaring their use in the document preamble:
  > This specification uses RFC 2119 keywords: MUST, MUST NOT, REQUIRED, SHALL, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL.
- Prefer **active voice** and short sentences.
- Avoid conversational hedges, motivational context, or historical anecdotes in normative sections. If background is needed, mark it clearly as non-normative (e.g., an `> **Note:**` block).
- Do not use first-person plural ("we", "our"). Address the implementer directly or use passive constructions.

| Avoid | Prefer |
|-------|--------|
| "We recommend that apps..." | "Applications SHOULD..." |
| "As mentioned above..." | *(restructure to avoid back-references)* |
| "In essence, this does X." | "This property specifies X." |
| "For now, we only use it for..." | "Currently used for X." |

### Document Structure

Organize the document top-down from most to least fundamental:

1. **Overview** — one paragraph: what the format is, what problem it solves, key links (schema, vocabulary)
2. **Format Requirements** — encoding, MIME type, file extension
3. **Top-level object** — required fields, prohibited fields, minimal example
4. **Object type definitions** — one subsection per named type, in dependency order (define before using)
5. **Cross-cutting concerns** — identifiers, measurements, custom types
6. **Complete examples** — whole valid documents, not fragments
7. **Validation** — how to verify conformance
8. **References** — external standards, related documents

Use **numbered sections** (`## 1.`, `### 1.1`) so implementations and issues can cite stable locations.

### Type Definitions

Each named type gets a subsection with:

1. A one-sentence definition
2. A **property table** with columns: Property | Type | Required | Description
3. Any additional constraints that cannot be expressed in the table
4. A minimal JSON example

**Property table format:**

| Property | Type | Required | Description |
|----------|------|----------|-------------|
| `id` | string | Yes | Unique identifier within scope |
| `mime` | MIME type string | No | Media type of the document |
| `location` | URI string | Conditional | Required for external documents |

- Mark **all** properties, including inherited and optional ones
- Use "Yes / No / Conditional" in the Required column; explain conditions in a constraints list below the table
- Reference other type definitions with anchored links (e.g., `[ViewMetadata](#52-viewmetadata)`)
- State explicitly when additional properties are **NOT allowed**

### Examples

- Use examples to **illustrate syntax**, not to motivate why the feature exists
- Every example MUST be valid against the JSON schema
- Keep examples **minimal**: include only the fields relevant to the point being made
- Provide at least one **complete** document example (all required fields) per format version
- Use placeholder variables (`$VERSION`, `$TypeName_VER`) consistently; `build.py` replaces them at release

### What Not to Include

Specifications are not the right place for:

- **Motivational prose** ("The reason we designed X this way is...")
- **Future plans** ("In a future version, we may add...")
- **Implementation guidance** ("When building an app, you should think about...")
- **Tutorial walkthroughs** (publish these separately as guides or examples)
- **Unresolved design questions** (resolve them before merging)

### Checklist Before Submitting Spec Changes

- [ ] All normative requirements use RFC 2119 keywords
- [ ] Every named type has a property table
- [ ] No required fields are undocumented
- [ ] All constraints expressed in the JSON schema are reflected in the spec
- [ ] Every JSON example is valid against `schema/mmif.json`
- [ ] No conversational or tutorial-style prose in normative sections
- [ ] Sections are numbered and linked correctly in the table of contents
- [ ] CHANGELOG.md updated
